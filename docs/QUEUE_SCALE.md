# 来源队列规模验证（M29，2026-10-09）

基线为 Explain `d33a78655f6742532ac070d84ddb9192248add2c`，对照 M29 的队列实现。原始样本、Node 版本及队列源码 SHA-256 见 [修改前](./assets/queue-scale-20261009/before.json) 和 [修改后](./assets/queue-scale-20261009/after.json)。这是 macOS / Node 24.20.0 的完全合成测量，不读取用户 Session、数据库、provider 或凭证。

## 测量方法

每个规模与场景启动五个独立 Node 子进程，先用 1,000 次操作预热并清空，再强制 GC 两次作为基线；完成操作后再强制 GC 两次。记录仍被队列引用的来源数量、堆增量和循环用时，中位数如下。`queued` 只入队；`processed` 每次取出并结束候选；`in-flight` 保留一个已取出的不同来源，再加入其余来源。待处理上限均为 8。修改前没有结束接口，因此 `processed` 保持旧行为。堆增量包含运行环境与 JIT 的保留分配；不是纯数据结构的精确字节数。用时只覆盖操作循环，排除进程启动与 GC，亚毫秒差异不据此解释为吞吐提升。

| 场景 | 来源数 | 保留来源：前 → 后 | 堆增量 KiB：前 → 后 | 循环 ms：前 → 后 |
|---|---:|---:|---:|---:|
| queued | 1,000 | 1,000 → 8 | 153.8 → 75.1 | 0.550 → 0.520 |
| queued | 10,000 | 10,000 → 8 | 1069.1 → 84.6 | 4.327 → 4.027 |
| processed | 1,000 | 1,000 → 0 | 152.4 → 69.3 | 0.188 → 0.179 |
| processed | 10,000 | 10,000 → 0 | 1064.9 → 70.9 | 2.823 → 2.655 |
| in-flight | 1,000 | 1,001 → 9 | 153.7 → 75.7 | 0.621 → 0.810 |
| in-flight | 10,000 | 10,001 → 9 | 1069.2 → 83.4 | 7.093 → 4.125 |

## 结论与行为约束

修改后保留身份不再随已见来源累计增长：仅入队时为 8、逐个处理结束后为 0、保留一个有效在途候选时为 9。生产 scheduler 全局单飞，并在每次自主候选执行后的 `finally` 调用 `finish()`；完成或终止失败后释放身份，已排队的 retry/defer 和新 turn 保持有效。淘汰及 trim 同时使旧目标失效；retry/defer 再次遵守最新容量，不能复活被淘汰或清除的候选。队列使用者必须为每个取出的候选调用结束接口；一般化的多个在途使用者需将其在途数量计入状态上界。

回归覆盖 10,000 个不同来源、有在途请求时的容量、逐个完成、满队列 retry/defer、淘汰后复活、重试尝试计数、旧候选结束不能删除新 turn、clear 后不复活，以及实际 scheduler 成功、终止失败和清除后的释放。全局单飞、Topic/来源门、额度与迟到结果 fencing 保持。
