    - text: 来源 real-v03… · 当前 学习回答 回合 1
    - time: 2026/9/15 17:27:22
    - text: 当前
    - heading "是什么" [level=4]
    - paragraph: "TypeScript 的类型系统只在编译期（类型检查阶段）生效：编译器把你的代码与类型标注做比对，发现属性不存在就报错。但这些类型标注在编译输出后会被完全擦除，生成的 JavaScript 里没有任何类型信息，所以运行时对象长什么样，就完全取决于实际赋值时写了什么字段。以 Result 为例，{ kind: \"error\", message: \"...\" } 在运行时压根没有 value 这个属性；TS 之所以禁止在收窄前访问 r.value，是因为它知道运行时可能真的取到 undefined，而不是因为运行时能替你补上 value。"
    - heading "为什么" [level=4]
    - paragraph: "把“编译期报错”和“运行时行为”分开，才能理解两条关键规则：第一，`Property 'value' does not exist on type 'Result'` 是编译器在拦你，不是运行时错误；第二，类型收窄（if (r.kind === \"ok\")）也只改变编译器的认知，不会改变运行时对象。这样你就能预判哪些错误会在编辑器里被抓住、哪些只会在运行时暴露（例如从 JSON.parse 或接口拿到的数据，类型标注只是你的断言，不会自动校验或补齐字段）。"
    - heading "常见坑" [level=4]
    - paragraph: 常见误解是“我给它标了类型，运行时它就会自动带上这些属性”。实际上类型标注不会创建字段、不会做运行时校验、也不会把 error 分支补出一个 value：错误写法里 if 分支外用 r.value 会在类型层面被拒绝，但如果你强行用 as any 绕过编译，运行时拿到的仍是 undefined，报错会推迟到运行时（比如 undefined.toFixed 抛异常）。正确做法是老老实实先用 kind 判别再访问，必要时在运行时边界（如接口返回）做真实的数据校验。
